# L'Ordre Déchu : règles du dépôt

RPG au tour par tour (combat ATB) en TypeScript strict, modules ES, build Vite, publié sur GitHub Pages.

## Suivi
- Tickets dans YouTrack, projet **MAE**.
- Parcours d'un ticket : /task-flow au début, /lead-review puis /git-commit avant chaque commit.
- Statuts : Open → In Progress → To Verify → Done.
- Done seulement quand le code est sur `main`, le déploiement GitHub Pages réussi et la vérification sur le site en ligne faite.
- Le passage en Done se fait uniquement sur le « oui » de Wesley.

## Méthode
Règle de Wesley du 03/11/2026, pour tous les tickets :
- Avant la fusion, ce sont les tests automatiques de Claude (bot, comparaisons mot pour mot, débordements) qui vérifient les règles du combat. Wesley valide sur le rapport de Claude et l'avis de claude.ai ; il ne joue plus lui-même pour tester ces règles.
- Le jugement visuel reste à Wesley : un changement qui se voit (interface, images, scène) est regardé à l'œil par Wesley une fois avant la fusion, sur son PC et son iPhone 11 si le ticket le demande (précision du 07/11/2026, MAE-87).
- Après la mise en ligne, des testeurs humains jouent sur le site, à vitesse normale. Un problème qu'ils trouvent devient un nouveau ticket.
- Un ticket passe en Done après la fusion, le déploiement et le contrôle en ligne de Claude, comme avant.

## Tickets
- Format des nouveaux tickets, et d'un ticket existant quand on l'ouvre avec /task-flow. Pas de réécriture en masse.
- Champs : Type, State, Priority, Assignee.
- Titre : un verbe à l'impératif suivi de l'objet concret, compréhensible sans jargon.
- Description, dans cet ordre (Contexte, Décisions et Hors périmètre si besoin) :
  - `Version : vX` en tête
  - `## Objectif`
  - `## Contexte`
  - `## Décisions du JJ/MM/AAAA`
  - `## Critères d'acceptation` (cases à cocher)
  - `## Hors périmètre`

## Branches
- Branche principale : `main`.
- Une branche par ticket, `type/description` depuis `main` (ex. `refactor/vite-es-modules`), puis PR vers `main`.
- Rien ne se commite directement sur `main`.

## Commandes
| Commande | Rôle |
|---|---|
| `npm install` | Installer les dépendances |
| `npm run dev` | Serveur de développement : `http://localhost:5173/ordre-dechu/` |
| `npm run build` | Build de production dans `dist/` |
| `npm run preview` | Servir `dist/` comme sur GitHub Pages |
| `npm run lint` | Vérifier le code avec ESLint (règles recommandées et règles de ce fichier, `eslint.config.js`, MAE-23) |
| `npm run typecheck` | Vérifier les types (`tsc --noEmit`, TypeScript 7) |
| `npm test` | Lancer les tests Vitest des règles du combat (dégâts, critiques, jauge ATB), une fois, sans mode surveillance (MAE-22) |
| `npm run check:battle` | Jouer un combat complet de chaque chapitre sous Node, sans navigateur, avec la vue muette (MAE-21) ; `-- <graine>` pour rejouer la même partie |

Mode test (MAE-68), en local seulement (`npm run dev` ou `npm run preview`), inerte sur le site en ligne :
```
http://localhost:5173/ordre-dechu/?chapitre=4&vitesse=4
```
- `chapitre=N` (1 à 7, numéro du titre) : « Nouvelle partie » démarre au chapitre N, sans prologue. Chaque héros a l'XP de tous les combats précédents, ses PV et PS pleins, et les objets de départ (sans les objets trouvés, ni la Larme dorée de l'écho) ; le groupe a les Couronnes de ces combats.
- `vitesse=X` (1 à 10) : durées, jauges ATB, animations CSS et gestes des combattants X fois plus rapides ; chaque page de dialogue attend toujours la validation. La vitesse du mode test sert au bot : en vitesse 4, le combat va plus vite qu'un humain ne peut suivre entre deux menus (menu ouvert, le temps reste arrêté, mode Attente, MAE-91). L'équilibrage devant le Dragon se valide par des testeurs humains à vitesse normale, après la mise en ligne, pas seulement par le bot (décisions du 03/11/2026, voir « Méthode »).
- `pouvoir=pris` ou `pouvoir=refuse` (MAE-72) : la partie démarre avec le pouvoir du Cœur d'Aure-Hin déjà pris ou refusé, pour atteindre les quatre fins avec `chapitre=7` sans rejouer le choix du chapitre IV.
- `combat=gagne` (MAE-72) : dans chaque combat, l'ennemi tombe à 0 PV dès le début ; la suite se joue normalement (récompenses, choix face au Dragon, scènes, épilogues). Pour jouer les fins sans combattre, avec `chapitre=7`.
- `combat=perdu` (MAE-87) : dans chaque combat, les héros tombent à 0 PV dès le début, pour atteindre l'écran de défaite sans jouer.
- `scene=lisiere` (MAE-28) : affiche le décor seul, à la place du jeu, avec un compteur d'images/s à l'écran et les personnages du chapitre. Touche P : la caméra oscille pour montrer le relief. `qualite=1`, `2` ou `3` en plus : niveau de qualité du décor (`CONFIG.scene.qualityLevels`, 2 par défaut partout), affiché dans le compteur ; les sprites restent à pleine résolution. Les personnages y respirent comme en combat (MAE-30). `verif=1` en plus : sans compteur, mesures pour le bot (`data-verif` sur `body`, `window.scenePreview`), à comparer aux PNG avec `tools/check-sprite-sharpness.mjs` du labo (capture prise avec le mouvement réduit, personnages au repos).
- `rendu=dom` (MAE-29) : les chapitres qui ont un décor s'affichent quand même en DOM, comme avant la scène peinte. Pour comparer deux versions du jeu avec le bot du labo.
- `decor=lisiere` (MAE-95) : ce décor peint pour chaque chapitre, même sans décor déclaré, pour voir dans la scène peinte les combats qui se jouent en DOM (le Dragon au chapitre VII, l'écho de Maelor au chapitre IV). Sans effet avec `scene=` ou `animations=1`, qui remplacent le jeu ; `rendu=dom` l'emporte sur lui.
- `animations=1` (MAE-30) : à la place du jeu, chaque combattant joue chacune de ses animations en boucle, dans sa case (attente, attaque, sort, dégâts, en danger, K.O. et réanimation, victoire ; pour les ennemis, mort, et pour le Dragon, vaincu puis épargné), et les effets spéciaux (MAE-95) : la Nuée de cendre du Dragon vers un héros posé dans sa case, l'écho de Maelor qui se défait en lumière, l'or qui quitte Maelor vers un Dragon posé dans sa case, puis sans Dragon (l'éclat seul). En bas de la page, chaque effet de capacité (MAE-31) joue en boucle sur ce que la capacité vise (un ennemi, deux pour Édrag et Soufre, un héros pour Nios, Sève ou Encens, les trois pour Aurésor, un héros au sol pour Liéver et la Larme dorée, et l'entaille reçue par un héros), puis chaque capacité des ennemis (MAE-98) sur un héros (les trois pour la Nuée de cendre), avec le nom de l'ennemi qui la lance. Tout en bas, le sang doré (MAE-98) : en tête, le risque noté par Wesley (les braises d'Elwen sont du même or vif que son sang) ; des curseurs pour les éclats de Maelor et d'Elwen (nombre, taille, durée, luminosité), qui les changent tout de suite, sans rien enregistrer, et affichent la ligne `goldBlood` à recopier dans leur fiche ; puis leur coup reçu en boucle, avec les braises d'Elwen et la teinte du coup reçu sous ses deux formes : le filtre CSS de la scène DOM, et la scène peinte imitée sur une copie de la toile (`paintedTint`). `zoom=1` à `4` en plus : pixels CSS par pixel de sprite (2 par défaut sur ordinateur, 1 sur téléphone). Une case à cocher simule le mouvement réduit pour toute la page. Sur téléphone : `npm run preview -- --host`, puis l'adresse `Network` suivie de `?animations=1`.
- `compteur=1` (MAE-29) : compteur d'images/s à l'écran pendant les chapitres joués dans la scène peinte, pour mesurer sur un téléphone avec le HUD. Il est devant l'interface, en haut à droite : sous le bandeau du groupe sur téléphone, sous le bouton du son sur ordinateur (MAE-31 : posé dans la scène, il était caché par la plaque du groupe). En mode test, la scène peinte expose aussi ses mesures au bot (`window.battleStage.measure()`).
- Test sur un téléphone en Wi-Fi : `npm run preview -- --host`, puis ouvrir sur le téléphone l'adresse `Network` affichée, suivie de `?scene=lisiere`. Le mode test accepte aussi les adresses privées du réseau local (`192.168.*`, `10.*`, `172.16-31.*`). Fermer le serveur après le test.
- Les paramètres se combinent ou s'utilisent seuls. Le titre de l'onglet commence alors par « [Test] ». Une valeur invalide est ignorée, avec un avertissement dans la console.
- En mode test, la sauvegarde du navigateur (MAE-11) n'est ni lue ni écrite, et « Continuer » est masqué. Pour tester la reprise, placer une sauvegarde (clé `ordre-dechu-save`) puis ouvrir le jeu sans paramètre.
- Tests automatisés dans un navigateur invisible (headless) : toujours lancé sans le son (`--mute-audio`), pour que le jeu ne s'entende pas pendant les tests (décision de Wesley du 02/11/2026).

Les tests sont dans `src/dev/*.test.ts`, sous Node, sans DOM : hasard par `vi.spyOn` sur `Math.random` (`src/dev/test-helpers.ts`), combat par la vue muette. Un test peut lire la feuille de style ou un fichier du code comme du texte (`?raw`), pour vérifier qu'ils s'accordent (`src/dev/tints.test.ts`) : c'est le réglage `test.css` de `vite.config.ts` qui le permet, sans lui Vitest vide tout fichier CSS.

Scène peinte en combat (MAE-29) : un chapitre qui déclare un décor (`decor` dans `CHAPTERS`, le chapitre I aujourd'hui) se joue dans la scène peinte en 2,5D ; les autres gardent le rendu DOM. Three.js et le décor se chargent au début de ce chapitre (`GameView.showChapter` est asynchrone), et si WebGL manque ou si le chargement échoue, le jeu se replie sur le DOM pour la partie. La scène couvre tout l'écran derrière l'interface DOM, et la peinture est cadrée dans le rectangle de `#battle-scene`, lui aussi en plein écran. Sur chaque combattant, une ancre DOM (`.actor-anchor[data-sprite]`) suit le sprite : chiffres, marques ▼, barre de vie, bouclier et toucher de ciblage passent par elle. La partie « scène » de l'affichage est le contrat `Stage` (`src/ui/stage.ts`), avec deux versions : DOM (`stage.ts`) et peinte (`src/scene/battle-stage.ts`) ; `dom-view.ts` choisit par chapitre et joue les sons au même rang pour les deux. Les effets des capacités : voir « Effets des capacités » plus bas (MAE-31).

Animations des combattants (MAE-30), dans les deux scènes, avec les mêmes images : chaque combattant est un canvas animé (`src/ui/animated-sprite.ts`, une seule boucle `requestAnimationFrame` pour tous, redessin seulement quand la pose change, au plus 12 fois par seconde). Chaque pixel affiché vient du PNG : une pose déplace des rangées entières d'un nombre entier de pixels, en répète ou en retire, sans lissage, sans agrandissement non entier, sans rotation (`src/ui/sprite-frames.ts`, testé sur les 9 sprites). Une pose de fond (attente, en danger, à terre, vaincu...) et un geste par-dessus (attaque, sort, coup reçu, chute, réanimation, victoire...) sont décrits dans `src/ui/sprite-motion.ts`, sans DOM, avec leurs durées lues dans `CONFIG.timing` : les animations ne lisent jamais l'horloge du combat, n'ajoutent aucune attente, et continuent pendant le mode Attente. Chaque personnage a un squelette (`rig` dans `HEROES` et `ENEMIES` : rangée de la taille, respiration). Chaque scène lance les gestes aux événements du combat ; `followHero` (`src/ui/hero-pose.ts`, sans DOM) tient la pose de fond des héros (à terre, en danger, qui agit ; à la victoire, un héros en danger passe debout). Les scènes posent aussi les couleurs (teinte du coup reçu, éclair, mort) et les glissements, par pixels de sprite entiers. Poses dessinées des héros (MAE-94) : à genoux en danger, au sol au K.O., flanche puis à genoux pendant la chute, à genoux pendant la réanimation, chacune un PNG (`public/images/<id>-stagger.png`, `-kneel.png`, `-down.png`) déclaré dans `rig.poses` (`HEROES`), recopié tel quel, centré sur le PNG debout, le bas sur la même rangée ; la toile s'élargit des deux côtés pour la plus large. L'ombre au sol suit l'empreinte de la pose, les braises d'Elwen s'éteignent sur ces poses (`data-pose`) et le contour du survol suit l'image affichée. Les images viennent de poses Gemini réduites dans le labo (`tools/reduce-poses.mjs`, repères `references/mae94/reperes.json`, planche de contrôle `references/sprites/mae94/planche.png`).

Effets spéciaux du combat (MAE-95), dans les deux scènes, dessinés en code pixel par pixel : la Nuée de cendre du Dragon (de sa gueule, `mouth` dans `ENEMIES`, vers les héros visés, au début de son sort ; son impact sur les héros touchés est l'effet de la capacité, `cinder`, MAE-98), l'écho de Maelor vaincu qui se défait en lumière (`vanish: "light"`, geste `unravel` : il passe en or, ses rangées s'effacent depuis le haut en lâchant des pixels dorés ; la lueur qui reste jusqu'au choix du pouvoir est MAE-97) et l'or qui quitte Maelor quand il rend le pouvoir (`Stage.powerReturn` : de la poitrine de Maelor telle qu'elle est affichée vers le Dragon à l'écran, avec un éclat doré ; l'or se pose sur les pixels opaques de la moitié basse de son image affaissée, ou sur le sol devant lui ; sans Dragon, l'éclat seul). La lumière de l'écho et l'or partent et se posent sur les pixels opaques exacts de chaque rangée (`opaqueRuns`, `src/ui/sprite-frames.ts`) ; les grains de cendre se posent dans le haut du rectangle de chaque héros. Les pixels de chaque image sont calculés sans DOM dans `src/ui/battle-fx.ts`, aux couleurs des fiches, sur la grille de 12 images/s, avec un générateur à graine propre, jamais `Math.random` (testé : un tirage de plus décalerait le hasard du combat et le bot). Ils sont dessinés dans une couche canvas posée sur la scène (`src/ui/fx-layer.ts`, `#battle-scene` en DOM, `#actor-layer` dans la scène peinte), un pixel du canvas par pixel de sprite, agrandie d'un nombre entier de pixels réels et calée sur le sprite d'où part l'effet, retirée à la fin. Son pixel est celui des sprites de la scène : en DOM, leur `--px`, qui vaut `--scene-px` sur ordinateur et 1 sur téléphone (corrigé avec MAE-31 : sur l'iPhone 11, la couche était 2,5 fois trop grande). Seule la disparition de l'écho est attendue (`CONFIG.timing.unravel`), en fin de son combat où il est seul ; la cendre et l'or ne sont pas attendus. Avec le mouvement réduit : un voile de cendre fixe, l'écho en or qui disparaît d'un coup, l'éclat de Maelor seul. En DOM, chaque sprite a son propre empilement : la couche passe devant les marques ▼ et les barres des ennemis le temps d'un effet ; dans la scène peinte, ils restent devant elle. Les chiffres, eux, restent devant la couche dans les deux scènes (MAE-31, voir plus bas). Contrôle en navigateur : `tools/fx-check.mjs` du labo (`ash`, `light`, `gold`, `framing`), qui vérifie aussi que le pixel de la couche est celui des sprites.

Effets des capacités (MAE-31), dans les deux scènes, sur le socle des effets spéciaux : une capacité déclare son effet dans les données (`effect`, de type `AbilityEffect`, dans `ATTACK`, `SPELLS`, `ITEMS` et `ENEMY_SKILLS`, `src/data/game-data.ts` ; un objet arrive à l'affichage comme une capacité), et son dessin est une fonction sans DOM de `src/ui/battle-fx.ts` (`ABILITY_FX` ; ajouter une capacité : un nom dans `AbilityEffect`, un dessin là). Chaque capacité (sauf le Repli, qui ne touche personne) et chaque objet a le sien, distinct (testé) : l'entaille de Frapper (`slash`), que montre aussi toute attaque simple d'un ennemi, et tout coup physique qui ne déclare pas d'effet ; Vordrak (`twin`, deux entailles bordées du rouge vin de Maelor) et Édrag (`sweep`, un arc qui balaie les ennemis) ; les quatre sorts de Corvin, Mèche (`wick`), Nuit blanche (`frost`), Tocsin (`bell`) et Soufre (`sulfur`) ; les trois d'Elwen, en or, Nios (`mend`), Aurésor (`dew`) et Liéver (`wake`) ; les objets Sève (`sap`), Encens (`incense`) et Larme dorée (`tear`) ; et les capacités des ennemis (MAE-98, décisions de Wesley du 11/11/2026) : aux couleurs des ennemis avec l'os gris pour arête claire, Chaînes (`chains`, un coup de fouet de maillons fer et rouille à hauteur de poitrine, qui retombent jusqu'aux pieds) et Pilier (`pillar`, un bloc cannelé qui tombe sur la tête et se brise, la poussière aux pieds) ; Kardrov (`echo`, Vordrak retourné de haut en bas dans la rampe d'or de l'écho, sans rouge vin ni or vif ; à l'écran, le sens du coup le retourne déjà de gauche à droite, il a donc la même diagonale que Vordrak sur un ennemi, tracée de bas en haut : `doubleCut` et ses styles `VORDRAK`, `KARDROV`) ; l'impact de la Nuée de cendre (`cinder`, des braises sombres sur le haut des héros touchés, qui s'éteignent en cendre qui tombe, sans couleur claire). Il n'y a plus aucun halo CSS (MAE-98) : une capacité sans `effect` n'aurait rien à l'écran, sans aucune erreur (sauf un coup physique, qui retombe sur l'entaille, `abilityEffect`). Toute nouvelle capacité déclare donc son `effect` : un sort, un objet ou une capacité d'ennemi qui l'oublie ne compile pas (types `Spell`, `Item` et `EnemySkill`, `game-data.ts`). L'effet est lancé sur ceux que la capacité touche (`Stage.impact`, puis `playAbilityFx`, `src/ui/stage.ts`), dessiné sur leur silhouette telle qu'elle est affichée (pixels opaques, `AnimatedSprite.shownRows`), le coup venant du camp d'en face. Règles (décisions de Wesley du 10/11/2026) : les couleurs viennent de la palette des personnages seulement, sans orange ni vert (le feu de Corvin est bleu pâle, testé) ; sur un « Raté », l'effet ne joue pas, et sur un « Sans effet » il joue, par exemple Liéver ou la Larme dorée sur un allié debout (`touched`, testé) ; aucun effet n'ajoute d'attente : il n'est jamais attendu. À vitesse normale, il dure huit images de la grille (`CONFIG.timing.abilityFx`) et il est retiré au plus tard à la fin de la pause de lecture des chiffres (testé) ; en mode test accéléré (`vitesse=X`), la grille reste à 12 images/s : un effet peut dépasser la pause et deux effets se chevaucher, sans casse. Aucun `Math.random` (testé). Avec le mouvement réduit : l'image la plus fournie de l'effet, fixe (`still`). Tant qu'il joue, la couche porte le nom de l'effet et de ses cibles (`data-fx`, par exemple `wick:sankri-0`), pour les contrôles en navigateur et le bot du labo ; le jeu ne s'en sert pas. Les chiffres restent devant les effets : dans la scène peinte ils sont sur l'ancre, et en scène DOM ils sont posés dans une couche à part au-dessus de celle des effets (`Stage.popupAnchor`, `.popup-layer`, une boîte par combattant, placée sur le rectangle de son sprite au moment où le chiffre naît, sans le suivre ensuite). En scène DOM, un chiffre n'est donc plus un enfant du sprite : la boîte dit de qui il est (`data-popup-for`). `#battle-scene` a son propre empilement (`isolation`), pour que cette couche reste sous les plaques de l'interface. L'animation des chiffres est à MAE-99. Contrôle en navigateur : `tools/ability-fx-check.mjs` du labo (un vrai combat par effet, dans les deux scènes, en 1600 × 900 et 390 × 844 ; `SLOW=1` pour des captures image par image).

Sang doré (MAE-98, décisions de Wesley du 10 et du 11/11/2026) : Maelor (héritage lointain) et Elwen (une immortelle) ont le sang doré. À chaque dégât reçu par l'un d'eux, physique ou magique, dès le chapitre I, quelques petits éclats d'or jaillissent de son torse tel qu'il est affiché, dans le sens du coup, puis retombent, dans les deux scènes. C'est un indice discret, jamais une révélation : rien dans l'histoire, l'interface, la chronique (`docs/historique.md`) ni le README ne le signale, et cela doit le rester. Les éclats n'ont que l'or ancien et l'or vif, sans transparence ; la luminosité est la part d'or vif (Elwen surtout en or vif, Maelor surtout en or ancien). Intensité fixe : les mêmes éclats pour tout dégât (faible, critique, fatal, sous Garde). Rien pour Corvin ni pour un ennemi, l'écho de Maelor compris. Le réglage est dans la fiche du héros (`goldBlood` dans `HEROES` : nombre, taille, durée en images, part d'or vif), réglé à l'œil par Wesley dans `?animations=1` (il a gardé les valeurs de départ) ; un seul réglage pour l'ordinateur et le téléphone, où un pixel de sprite est plus petit. Le dessin est `goldBlood` (`src/ui/battle-fx.ts`, sans DOM, graine propre, au plus huit images, bornes `BLOOD_LIMITS`) ; les deux scènes le lancent depuis `hit`, donc jamais sur un « Raté », par `playGoldBlood` (`src/ui/stage.ts`, `goldBloodOf`), sans l'attendre, en image fixe avec le mouvement réduit ; la couche porte `blood:<id>`. Contrôles en navigateur du labo : `tools/ability-fx-check.mjs … blood` (en vrai combat : du sang à chaque dégât de Maelor et d'Elwen, jamais ailleurs), `tools/blood-preview-check.mjs` (la section de l'aperçu) et `tools/hit-tint-check.mjs` (le coup reçu en vrai combat, dans les deux scènes : braise et éclats sur la couche pour un héros, éclair parchemin sans sang pour un ennemi).

Mouvement réduit et teintes (MAE-31) : le réglage « mouvement réduit » se lit partout par `isReducedMotion()` (`src/ui/reduced-motion.ts`, sans DOM, avec la simulation de l'aperçu `?animations=1` et un abonnement aux changements pour la scène peinte) ; seuls les blocs `@media (prefers-reduced-motion)` de la feuille de style lisent le système directement. Les teintes passagères des combattants (l'or, la mort, le coup reçu par un héros, le coup reçu par un ennemi) sont définies une seule fois dans `src/ui/tints.ts`, sous leurs deux formes : le filtre CSS, que la scène DOM pose sur `#battle-scene` en variables `--tint-*` lues par `style.css` (sans elles, ces filtres ne s'appliqueraient pas) et que l'aperçu lit directement dans `TINTS` ; et la couleur, la part et l'éclat de la scène peinte. Le coup reçu (MAE-98, décisions de Wesley du 11/11/2026, à la place de l'ancien orange pour tous) : un rougeoiement de braise sur un héros (`TINTS.hit`), un éclair parchemin sur un ennemi (`TINTS.foeHit`, variable `--tint-foe-hit` : `tintVariables` écrit les noms en minuscules à tirets ; en DOM, la règle `.sprite.enemy.damaged`). Dans la scène peinte, mêler une couleur assombrissait les pixels clairs : chacune y colore donc la luminosité de chaque pixel (`gain`, en sRGB comme les filtres CSS), la braise de la teinte de la rouille des ennemis, la couleur de la palette la plus proche de son filtre CSS, l'éclair de celle du parchemin ; la scène peinte choisit la teinte selon le camp de celui qui est touché. En DOM, l'image d'un ennemi monte à sa teinte par une transition de 0,6 s (`.sprite.enemy .sprite-img`), plus longue que le coup reçu (0,4 s) : l'éclair n'y atteint pas tout son éclat, alors que la scène peinte le pose d'un coup. Cette formule est écrite une fois sans DOM (`paintedTint`), reproduite par le shader des sprites (`src/scene/actors.ts`), et testée, pour les deux teintes du coup reçu, contre le calcul du filtre CSS sur toutes les couleurs de la palette (`tints.test.ts`). `tints.ts` doit rester une feuille, sans import d'une scène ni de `view.ts`, comme `battle-fx.ts` dont il lit les couleurs : la scène peinte et l'aperçu lisent `TINTS` dès leur chargement, ce que la règle des modules ci-dessous ne permet qu'envers un module feuille. Contrôle en navigateur : `tools/tint-check.mjs` du labo (`tints`, `motion`), qui compare les filtres CSS posés par le jeu à ceux attendus ; il ne compare pas les deux scènes : pour le coup reçu, c'est `tools/hit-tint-check.mjs`.

Interface du combat (MAE-87), d'après les planches D2 et G1 à G7 : le groupe en haut à gauche et le menu en bas à gauche, sur des plaques d'ombre (`.hud-plate`), une marque ▼ qui suit le sprite (`overlayHtml`, `src/ui/stage.ts`), la barre du boss en bas au centre, et tous les dialogues dans une bande d'ombre en bas (le dessin des fragments de mémoire et des choix reste à MAE-51). Sur ordinateur, la hauteur de la bande et la taille de son texte suivent la hauteur de l'écran (`--band-height`, `--band-text`, `design-system.css`), et la peinture glisse pour garder les personnages au-dessus. Les plaques grandissent de la même façon (`--hud-text`, `--plate-width`, `--hud-width`). Sur un écran plus large que le 16:9, la peinture remplit tout l'écran et l'interface se place dans une zone centrale 16:9 (`--zone-width`, `--zone-left`) ; les combattants y sont déjà, car la peinture a ce format. Dans les deux scènes, un pixel de sprite fait un nombre entier de pixels réels. L'écran titre garde son ancien style et ses polices jusqu'à MAE-42 et MAE-49. Téléphone en portrait (planches P1 à P6) : tout écran de 640 px de large ou moins, dans le `@media` de la fin de `style.css` ; le groupe en haut, la scène au milieu, un panneau de hauteur fixe en bas pour le menu et la bande de dialogue. Le paysage reste à MAE-40.

Souris et clavier sur ordinateur (MAE-89, planches N1 et N2, plus de 640 px de large ; le téléphone garde son toucher) : dans la plaque du menu, la liste numérotée à gauche et l'aide à droite (`#battle-help` : l'entrée sous le curseur, avec élément et coût, et le rappel des touches pendant les combats du chapitre I) ; en ciblage, la liste d'où vient la capacité reste à gauche, en copie inerte (`#target-list`). Un clic sur un ennemi au menu principal lance Frapper, rien dans un sous-menu, et valide la cible en ciblage ; les touches 1 à 9 choisissent une entrée ; les flèches passent d'une cible à l'autre dans l'ordre de l'écran (`src/ui/target-order.ts`, testé). Au survol, un contour clair de lune (`--moonlight`) suit la silhouette du sprite, et « Clic : Frapper … » s'affiche quand le clic frappe. La barre du boss reste centrée quand elle a la place, sinon elle se pose à droite de la plaque la plus large (`--menu-plate-max`). Sur les écrans bas, le menu principal passe sur deux colonnes (800 px de haut ou moins) et la plaque se resserre (880 px ou moins), pour rester sous les pieds des héros. Les textes d'aide des commandes sont dans `COMMAND_HELP` (`src/data/game-data.ts`). Pendant les dialogues d'histoire, le groupe se cache, sur ordinateur comme sur téléphone (classe `story-dialog` sur `body`, posée par `dom-view.ts`) ; il reste au combat, à la victoire et à la montée de niveau.

Mode Attente (MAE-91, `CONFIG.atb.mode`, `isTimeFrozen` dans `src/battle/battle.ts`) : tant qu'un héros a son menu ouvert (menu principal, sous-menu ou ciblage), le temps du combat s'arrête, jauges et actions en file comprises ; avec plusieurs héros prêts, il ne reprend qu'une fois tous les ordres donnés, et la file garde son ordre. L'action déjà en cours d'animation, les animations d'ambiance et la musique continuent. Le mode « active » (le temps ne s'arrête que pendant une action) est gardé pour le choix du menu Options (MAE-81).

Polices : toutes hébergées dans `public/fonts/`, avec leur licence dans `public/licenses/`, aucune chargée depuis Internet (`src/styles/design-system.css`).

Vérification automatique (MAE-23) : `.github/workflows/ci.yml` lance lint, types, tests, `check:battle` (graine 2026) et build à chaque push et à chaque pull request ; `deploy.yml` lance les mêmes contrôles avant le build, et une erreur bloque la publication.

Version de Node : `.nvmrc` est la seule source, lue par `ci.yml` et `deploy.yml`, et le PC de Wesley a la même. Changer de version de Node se décide avec Wesley.

## Convention de noms
- Fichiers en minuscules avec tirets (kebab-case), en anglais, sans accents ni espaces.
- Code regroupé par domaine sous `src/` : `battle/`, `story/`, `party/`, `data/` (la logique : règles, état, histoire), `ui/` (l'affichage DOM : fenêtres, dialogue, menus de combat, scène DOM ; `dom-view.ts` implémente le contrat), `audio/`, `input/`, `styles/`, `scene/` (scène peinte en 2,5D et son branchement sur le combat, seul domaine à importer Three.js, jamais depuis le code de démarrage : toujours par `import()`), `dev/` (outils de test en local, dont la vue muette `silent-view.ts`, `headless-battle.ts` et les tests Vitest). Le contrat entre logique et affichage est `src/game-view.ts` ; celui entre l'affichage et sa scène est `src/ui/stage.ts`.
- Images dans `public/images/`, référencées en `images/...` dans le code et en `/images/...` dans le CSS.
- Musiques dans `public/audio/` (MP3 96 kbps stéréo), référencées en `audio/...` dans le code (`MUSIC`, `src/data/game-data.ts`).
- Identifiants en anglais ; textes affichés et commentaires en français.

## Modules
- Chaque fichier importe explicitement ce qu'il utilise, sans variable globale partagée.
- Aucun code exécuté au chargement d'un module ne doit appeler un autre module : les modules s'importent en boucle (combat, menu, affichage), et un tel appel tomberait sur une valeur pas encore initialisée. Le code de démarrage va dans `src/main.ts`.
- TypeScript strict : pas de `any`, pas de `!` (assertion non nulle), chaque `as` justifié en commentaire.
- Logique et affichage séparés (MAE-21) : `src/battle/`, `src/story/`, `src/party/` et `src/data/` ne touchent ni au DOM ni à Three.js (aucun `document`, aucun `three`, vérifiable par recherche) et n'importent rien de `ui/`, `audio/`, `scene/` ni `dev/` (sauf des types, par `import type`). La logique reçoit son affichage en paramètre (`startGame`, `runBattle`) et ne lui parle que par l'interface `GameView` de `src/game-view.ts`. L'affichage lit l'état (`GameState`, `Battle`) pour dessiner, mais ne le modifie pas : il rend les décisions du joueur (ordres de combat, choix) par des promesses. Sons et musiques sont du côté de l'affichage. Toute nouvelle sortie visuelle ou sonore passe par une méthode du contrat, implémentée dans `ui/dom-view.ts` et dans `dev/silent-view.ts`.

## Sauvegarde
